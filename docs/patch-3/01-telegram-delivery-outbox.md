# 01. Гарантированная доставка Telegram-сообщений

Статус: предложение к реализации
Приоритет: P0
Область: стабильность Telegram, восстановление после сетевых сбоев

## Проблема

Состояние попытки и ответа надёжно фиксируется в PostgreSQL, однако сообщение пользователю отправляется отдельно. После исчерпания коротких повторов неуспешная доставка остаётся только в логах. В результате ответ может быть уже обработан, но пользователь не получает следующий вопрос, ошибку или финальный результат.

Затрагиваемые участки:

- `apps/api/src/training/training-voice-worker.service.ts`;
- `apps/api/src/training/training-telegram.service.ts`;
- Telegram client и webhook controller;
- Prisma schema и новая additive migration.

## Целевое решение

Добавить узкий training-specific outbox исходящих уведомлений. Запись создаётся в той же транзакции, где меняется состояние попытки или ответа. Отдельный обработчик доставляет сообщение в Telegram с повторными попытками.

Минимальный контракт записи:

- внутренний `id`;
- `eventType`;
- `attemptId` и при необходимости `answerId`;
- детерминированный `deduplicationKey`;
- `status`, `attempts`, `availableAt`, `lockedAt`, `lockedBy`;
- безопасный `lastErrorCode`;
- timestamps.

Payload не должен содержать bot token, webhook secret, полную расшифровку, аудио или готовый Telegram request. Текст нужно строить из актуального доменного состояния непосредственно перед отправкой.

## Поведение

1. Доменная транзакция завершает обработку ответа и создаёт notification intent.
2. Worker получает intent через PostgreSQL claim с fencing token.
3. При временной ошибке используется exponential backoff с jitter.
4. После лимита попыток запись переходит в `FAILED`, но остаётся доступной для ручного retry.
5. Повторная обработка одного события не создаёт дубликат благодаря `deduplicationKey`.
6. Команда `/start` сверяет состояние и повторно показывает актуальный вопрос или результат независимо от outbox.

## Границы

- Не создавать универсальную очередь для всей платформы.
- Не переносить в outbox входящие Telegram update.
- Не менять правила оценки, попыток или доступа.
- Не считать доставку exactly-once: требуется at-least-once с идемпотентным формированием сообщений.

## Критерии приёмки

- Падение Telegram API после commit не теряет уведомление.
- Restart API/worker между commit и отправкой не теряет уведомление.
- Два worker не отправляют одно событие параллельно.
- Повторный claim после stale lock корректно восстанавливается.
- `/start` восстанавливает интерфейс даже при окончательно неуспешной доставке.
- Логи и API не раскрывают секреты или содержимое голосового ответа.

## Проверки

Нужны targeted PostgreSQL-тесты на commit/restart/concurrency/stale lock, HTTP-тесты webhook и fake Telegram-тесты. Реальный Telegram smoke выполняется отдельно и только после разрешения.
