# 06. Снижение ложных отправок на ручную проверку

Статус: предложение к реализации
Приоритет: P1
Область: review routing, unsupported claims, качество вопросов

## Проблема

Любой `unsupported_claim` автоматически делает весь ответ требующим ручной проверки. Для открытого MAIN-вопроса сотрудник естественно сообщает дополнительные сведения, поэтому ручной контур срабатывает слишком часто даже без противоречия эталонным фактам.

Основные участки:

- `training-openai-evaluator.ts`;
- `training-evaluator.ts`;
- `training-attempt-state.service.ts`;
- review UI и ranking consumers.

## Целевое решение

Разделить неподтверждённые утверждения по влиянию:

- `HARMLESS_EXTRA` — дополнительная информация, не влияющая на оценку;
- `MATERIAL_UNVERIFIED` — существенный факт, требующий проверки;
- `CONTRADICTORY` — противоречие утверждённому факту;
- `UNSAFE_TO_SCORE` — недостаточно данных для надёжной автоматической оценки.

Ручная проверка нужна для трёх последних категорий. `HARMLESS_EXTRA` фиксируется в безопасной внутренней аналитике, но не блокирует результат.

Дополнительно MAIN-вопрос следует сделать структурированнее: перечислить ожидаемые темы или ограничить ответ рамками, которые покрываются утверждёнными фактами.

## Quality gate

Перед включением правила сформировать небольшой набор реальных ответов с человеческими метками:

- должен ли ответ идти на review;
- есть ли материальное противоречие;
- допустима ли автоматическая оценка;
- итоговый score range.

Главная метрика — отсутствие false negative для материальных ошибок. Снижение review rate является вторичной метрикой.

## Границы

- Не считать неподтверждённый факт правильным.
- Не использовать внешние знания оценщика.
- Не менять окончательный score для уже завершённых попыток.
- Не раскрывать сотруднику внутренние причины review до решения администратора.

## Критерии приёмки

- Безобидная дополнительная фраза не блокирует ответ.
- Противоречие эталону всегда требует review или безопасно штрафуется действующим правилом.
- Поведение MAIN и FOLLOW_UP тестируется отдельно.
- Review routing детерминированно восстанавливается из сохранённого evaluation JSON.
- Ranking не использует неподтверждённый provisional result.
