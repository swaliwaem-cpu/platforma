# 09. Снижение idle polling-нагрузки worker

Статус: предложение к реализации
Приоритет: P2
Область: PostgreSQL polling, worker responsiveness

## Проблема

Voice worker опрашивает PostgreSQL с постоянным коротким интервалом даже при пустой очереди. На текущем объёме это не является bottleneck, но создаёт постоянные запросы и умножается на количество worker-инстансов.

Основной участок: `apps/api/src/training/training-voice-worker.service.ts`.

## Целевое решение

Использовать гибридную схему:

1. После создания PROCESSING answer выполнять мгновенный локальный `kick()`.
2. При найденной работе продолжать pump без задержки до заполнения concurrency.
3. При пустой очереди постепенно увеличивать интервал, например 2 → 5 → 10 → 15 секунд.
4. После любой найденной работы возвращаться к минимальному интервалу.
5. Сохранять периодический recovery sweep для stale claims.

При нескольких отдельных worker можно добавить PostgreSQL `LISTEN/NOTIFY` как сигнал пробуждения. `NOTIFY` не является источником истины: пропущенный сигнал должен компенсироваться периодическим polling.

## Границы

- Не переносить source of truth в Redis.
- Не удалять `FOR UPDATE SKIP LOCKED`, fencing token и stale recovery.
- Не увеличивать задержку первого ответа после `kick()`.

## Критерии приёмки

- Новая локальная работа начинается немедленно.
- При длительном простое число DB queries заметно уменьшается.
- Потерянный `NOTIFY` не оставляет ответ навсегда в PROCESSING.
- Два worker сохраняют текущие concurrency и ownership guarantees.
- Recovery exhausted/stale answers продолжает запускаться по расписанию.

## Проверки

Нужны fake-timer unit-тесты, PostgreSQL concurrency test и измерение числа claim-запросов за фиксированный idle-интервал.
