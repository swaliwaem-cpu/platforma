# Этап 4. Стабилизировать проверку fencing material worker

Приоритет: P1

Тип работы: ограниченная диагностика race и точечное исправление

Production: запрещён

## Промт этапа

```text
Цель: определить, является ли нестабильность fencing-теста только гонкой test harness или реальным дефектом material worker, и исправить доказанную первопричину без ослабления concurrency guarantees.

Исходные наблюдения предыдущего аудита, которые нужно перепроверить:

- `apps/api/tests/training-material-operations-postgres.test.cjs` содержит сценарий `a worker that loses its fencing token cannot finalize a replacement claim`;
- один полный прогон проходил 5/5;
- повтор полного файла дал 4/5 и timeout около 45 секунд именно в fencing-сценарии;
- немедленный изолированный повтор прошёл примерно за 143 мс;
- причина пока не доказана.

Порядок работы:

1. Один read-only субагент анализирует worker claim/fencing/heartbeat/stale recovery код, второй — lifecycle test fixture, DB isolation и cleanup. Они ничего не меняют.
2. Главный агент строит timeline фаз `claim` → `waitUntilStarted` → смена `lockedBy` → release barrier → завершение `runOnce` → финальное чтение и перечисляет транзакции, timers, locks и условия выхода.
3. Запусти ограниченную диагностику: один isolated run, один full-file run и затем максимум пять последовательных повторов. До запусков зафиксируй лимит; не продолжай бесконечно ради случайного падения.
4. Добавляй только безопасную диагностическую информацию без payload, секретов и больших логов. Удаляй временную диагностику, если она не является полезной частью теста.
5. Различи минимум три класса причин: неверное ожидание теста, утечка ресурсов/таймера между тестами, реальная потеря fencing/stale claim в production-коде.
6. Меняй production-код только при воспроизводимом доказательстве его дефекта. Иначе исправляй исключительно test orchestration.
7. Не заменяй причинное ожидание произвольным sleep. Используй наблюдаемое состояние/барьер и bounded polling. Test barrier обязательно освобождай в `finally`, чтобы ошибка fixture не оставляла heartbeat или незавершённый `runOnce`.
8. После исправления read-only субагент проверяет, что stale worker всё ещё не может finalize replacement claim и что cleanup не оставляет locks/connections/timers.

Нельзя:

- увеличивать timeout как единственное исправление;
- добавлять retry, который скрывает первый failed invariant;
- ослаблять fencing token, `SKIP LOCKED`, global capacity или stale recovery;
- ставить `.skip`/`.only`;
- запускать против общей или production БД;
- выполнять реальные provider calls.

Stop condition: если после лимитированных прогонов причина не воспроизводится и статический анализ не доказывает дефект, не вноси предположительное исправление. Остановись с timeline, собранными фактами и предложением следующей ограниченной диагностики.

Минимальные проверки после доказанного исправления:

- сначала `pnpm build:api`, потому что PostgreSQL-тест импортирует `apps/api/dist`;
- применить migrations только к чистой временной PostgreSQL;
- targeted проблемный сценарий с установленным `TRAINING_TEST_DATABASE_URL`; sentinel-запуск без этой переменной не считается DB-проверкой;
- полный `training-material-operations-postgres.test.cjs` на изолированной временной PostgreSQL;
- проверка отсутствия незакрытых test ресурсов;
- `git diff --check`.

Критерий завершения: причина доказана, исправление минимально, инвариант fencing продолжает проверяться, а результаты укладываются в заранее заданный лимит прогонов.

Если зависание связано с PostgreSQL lock/connection, сохрани фазу и query evidence и остановись до отдельного решения. Если исправление требует worker semantics, Prisma schema или migration, запроси подтверждение.
```
