## RealEstateObject lifecycle

Source files: `apps/api/src/objects/objects.service.ts`, `apps/api/src/objects/objects.controller.ts`, `apps/api/prisma/schema.prisma`.

1. Create: `POST /objects` creates `RealEstateObject` as `DRAFT`. A provided status must not contradict draft behavior.
2. Edit draft/published: `PATCH /objects/:id` updates scalar fields and links to developer/location/metro. If an object is already published, required publish fields cannot be removed.
3. Publish: `POST /objects/:id/publish` or `PATCH /objects/:id/status` to `PUBLISHED` validates title, slug, developer, primary location, address, latitude, longitude, and completion year/quarter consistency.
4. Archive: `PATCH /objects/:id/status` to `ARCHIVED` sets archive state/timestamp.
5. Media/files: object gallery and linked files attach `File` rows through `ObjectImage` and `ObjectFile`; gallery cover/sort/section is maintained in object service.
6. Import updates: `tools/wp-import/src/importer.ts` can upsert objects by `wpPostId`/slug and archive missing imported objects; `tools/feed-import/src/index.ts` updates feed-derived unit data and object feed summary fields.
7. Audit: object actions create `AuditLog` rows in `apps/api/src/objects/objects.service.ts`.

## Prisma to API response

Prisma model: `RealEstateObject` in `apps/api/prisma/schema.prisma`.

Serialization layer: `apps/api/src/objects/objects.service.ts` and `apps/api/src/map/map.service.ts`.

Important transformations:

- Decimal fields such as prices are serialized as strings.
- Coordinates are serialized as numbers for frontend map/detail.
- Nested developer/location/metro/image/file data is shaped into shared contracts from `packages/shared/src/index.ts`.
- `GET /objects` uses summary include set; `GET /objects/:id` and `GET /objects/slug/:slug` use detail include set.
- `GET /map/objects` returns `MapObject`, not full detail.
- Feed-derived values can override/fallback manual catalog values: confirmed in `apps/api/src/objects/objects.service.ts` and catalog tests `apps/web/tests/catalog-feed-fallback.test.mjs`.

## Frontend dependencies on backend response

High-sensitivity dependencies:

- `AuthResponse.user.permissions` drives route access in `apps/web/src/App.tsx` and `apps/web/src/auth/AuthProvider.tsx`.
- `RealEstateObjectSummary` drives catalog cards and admin quick edit in `apps/web/src/catalog/CatalogPage.tsx`, `apps/web/src/admin/ObjectQuickEditTable.tsx`.
- `RealEstateObjectDetail.images/files/locations/metroStations` drive detail and object form in `apps/web/src/objects/ObjectDetailPage.tsx`, `apps/web/src/admin/ObjectsAdminPage.tsx`.
- `FileVariant` names `thumbnail`, `card`, `detail`, `original` are used by `apps/web/src/files/SecureImage.tsx`.
- `MapObject.latitude/longitude/images` drive `apps/web/src/map/YandexMap.tsx`.
- Feed fields `effectivePrice`, `discountPrice`, `media.file`, `hasDiscountPrices` drive `ObjectFeedUnitsSection` in `apps/web/src/objects/ObjectDetailPage.tsx`.

## Shared type breakage points

Shared contracts live in `packages/shared/src/index.ts`. Changing them can break:

- Frontend compile/runtime: `apps/web/src/App.tsx`, `apps/web/src/catalog/CatalogPage.tsx`, `apps/web/src/admin`, `apps/web/src/objects`.
- Backend search normalization: `apps/api/src/search/search-filters.ts`, `apps/api/src/objects/object-search.ts`.
- Feed package contract: `tools/feed-import/tests/package-contract.test.cjs`.
- API contract tests: `apps/api/tests/api-contract.test.cjs`.

There is no generated OpenAPI schema found. DTO validation is mostly manual in services/controllers, so compatibility relies on shared types plus tests: неясно whether external consumers exist.

### Import data contracts

- WordPress reports use shared `ImportReport`, `ImportReportsResponse`, `ImportReportResponse` in `packages/shared/src/index.ts`; source rows live in `ImportReport` in `apps/api/prisma/schema.prisma`.
- Feed admin uses shared `FeedSource`, `FeedSourceMapping`, `FeedImportRun`, `FeedUnit`, `FeedSourceAnalysisResponse`, `FeedImportRunResponse`, `FeedUnitsResponse` in `packages/shared/src/index.ts`.
- WordPress source identity fields are `RealEstateObject.wpPostId`, `Location.wpTermId`, `MetroStation.wpTermId`, `File.wpAttachmentId` in `apps/api/prisma/schema.prisma`.
- Feed source identity fields are `FeedUnit` unique `[sourceId, externalId]`, `FeedMediaAsset.sourceUrl`, `FeedUnitMedia` composite `[unitId, mediaAssetId]`, `File` unique `[storage,bucket,key]` in `apps/api/prisma/schema.prisma`.
- Feed aggregate fields on `RealEstateObject` are refreshed by `refreshRealEstateObjectFeedAggregates()` in `tools/feed-import/src/index.ts` and consumed by object/catalog serializers in `apps/api/src/objects/objects.service.ts`.

### Import data risks

- API services orchestrate shell commands and find latest reports/runs, but write semantics live in `tools/wp-import/src/importer.ts` and `tools/feed-import/src/index.ts`.
- Preview modes still write report/run records: `ImportReport` for WordPress and `FeedImportRun` for feed, confirmed in `tools/wp-import/src/importer.ts` and `tools/feed-import/src/index.ts`.
- WordPress run can mutate `RealEstateObject` and related media; feed run mutates `FeedUnit` and object feed aggregate fields; both are visible in catalog/detail through `apps/api/src/objects/objects.service.ts`.
- Separate `/feed-import/preview` and `/feed-import/run` endpoints were not found in `apps/api/src`; the valid feed import API is `/feeds/sources/:id/preview|run` in `apps/api/src/feeds/feeds.controller.ts`.
