# Frontend Guide

## Общие правила

- Сохраняй существующий app shell и визуальный язык Platforma.
- Интерфейс должен оставаться рабочим,
  спокойным и насыщенным данными.
- Не превращай внутренние экраны в лендинг.
- Не добавляй generic AI-дизайн,
  случайные градиенты и стекломорфизм.
- Не меняй layout соседних разделов
  в рамках локальной задачи.

## Архитектура

- Используй существующий routing.
- Не подключай новую routing-библиотеку
  без отдельного решения.
- Используй существующий `AuthProvider` и API client.
- Не дублируй refresh и auth logic в отдельных страницах.
- Не добавляй новый global state manager
  без доказанной необходимости.
- Держи API contracts в `packages/shared`,
  только если они используются frontend и backend.

## Компоненты

- Страница отвечает за orchestration,
  а не за всю реализацию.
- Выноси независимые крупные блоки
  в предметные компоненты.
- Выноси повторяемую async-логику
  в узкие hooks.
- Не создавай один компонент на тысячи строк.
- Новый компонент более 500 строк требует объяснения.
- Не создавай десятки микрокомпонентов
  без самостоятельной ответственности.

## Async state

Для запросов учитывай:

- loading;
- empty;
- error;
- retry;
- stale response;
- unmount;
- `AbortController`,
  когда запрос может пережить компонент;
- race при смене entity или filter;
- очистку Blob и Object URLs.

Не полагайся только на порядок завершения Promise.

## Permissions

- Frontend permission gates отвечают только за UX.
- Backend остаётся источником авторизации.
- Прямой переход по URL
  не должен обходить backend RBAC.
- Не выводи чувствительные данные,
  которые frontend не должен получать вообще.

## Формы

- Backend validation является источником истины.
- Не скрывай backend error
  за общей надписью без необходимости.
- Не очищай форму после неуспешного сохранения.
- Не выполняй duplicate submit.
- Для идемпотентных операций
  сохраняй один ключ на весь retry одной операции.

## CSS

- Предпочитай локальные предметные классы.
- Не добавляй глобальные selectors без необходимости.
- Проверяй desktop и mobile.
- Сохраняй focus states, labels, контраст и touch targets.
- Учитывай `prefers-reduced-motion`.
- Не удаляй CSS только по отсутствию
  точного строкового совпадения:
  проверь conditional classes, `data-state`,
  Radix и runtime generation.

## Размер и структура файлов

- Не добавляй новую ответственность
  в уже крупную страницу.
- Не создавай generic `frontendUtils`.
- Форматтеры и view models
  называй по предметной области.
- Не смешивай API, state machine,
  markup и formatting в одном огромном файле.

## Проверки

После frontend-изменений:

- запусти targeted web tests;
- запусти web build;
- при изменении routes, auth или shared contracts
  запусти полный build;
- проверь loading, empty и error;
- проверь direct URL;
- проверь browser back/forward,
  если менялся routing;
- проверь mobile viewport;
- проверь доступ с разными permissions.

Не заменяй behavioral tests
только regex-проверками исходников,
если доступен runtime или browser test.
