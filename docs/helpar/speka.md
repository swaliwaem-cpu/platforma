# Спецификация: внутренний ИИ-помощник по недвижимости, умный поиск и геопоиск

Статус: утверждено для декомпозиции и реализации.

Этот документ объединяет общую спецификацию ИИ-помощника из GitHub issue #2 и уточняющую спецификацию карт и геопоиска из GitHub issue #3. Он является каноническим источником требований для последующей постановки задачи. При расхождении с исходными issue приоритет имеет этот документ; в части карт и геопоиска использованы более конкретные решения из issue #3.

## Problem Statement

Platforma является закрытой внутренней платформой для брокеров недвижимости, но поиск фактов, актуальных предложений и сравнений распределён между каталогом Platforma, официальными сайтами застройщиков, банковскими и партнёрскими предложениями, агрегаторами и отдельными PDF-презентациями.

Пользователю приходится вручную сопоставлять проекты, лоты, цены, наличие, ипотеку, рассрочки, бонусы, характеристики локации и информацию о жилом комплексе. Это медленно, неудобно и повышает риск показать клиенту устаревшую цену либо пропустить подходящее предложение, которого ещё нет в Platforma.

Нужен внутренний ИИ-помощник в формате умного поисковика. Он должен понимать естественный русский язык, искать только по доступным данным, сравнивать все подходящие варианты, задавать короткие уточнения, показывать лучшие результаты и честно обозначать отклонения и свежесть данных. Он не должен придумывать факты, выполнять действия от имени пользователя, заниматься юридическими или налоговыми консультациями либо перегружать интерфейс десятками ссылок.

Отдельная проблема — геопоиск. Пользователь должен иметь возможность запросить предложения возле метро, делового центра, адреса или выбранной вручную точки, например «возле Павелецкая Плаза в радиусе 2 км».

Текущая Platforma использует Yandex Maps JS API для карты каталога и карты в карточке объекта. Это создаёт внешнюю коммерческую зависимость, требует frontend API key и может привести к непропорциональным расходам при росте количества пользователей и просмотров. Текущая карта также не умеет разрешать название произвольного места и выполнять индексированный радиусный запрос PostGIS.

## Solution

Добавить во все авторизованные страницы Platforma плавающий чат с внутренним ИИ-помощником. Помощник отвечает на тематические вопросы по недвижимости, выполняет структурированный поиск и сравнение проектов и лотов, поддерживает поиск вокруг текстового места или выбранной вручную точки и использует только найденные доказательства.

Основой решения является гибридный retrieval:

- структурированные SQL-фильтры и актуальные FeedUnit из Platforma;
- полнотекстовый поиск PostgreSQL;
- семантический поиск через pgvector;
- версионированные факты и chunks из внешних источников;
- пространственный поиск PostGIS.

Модель используется для понимания запроса, составления структурированного намерения, объяснения сравнения и формирования ответа. Модель не является источником координат, цен, наличия, ссылок или фактов.

Обычные запросы обслуживаются Luna с reasoning medium. Сложные сравнения и поиск спрятанных условий обслуживаются Luna с reasoning high. После детерминированной проверки допускается один fallback на Terra с reasoning medium. Luna max не используется.

Пользователь получает максимум три основных результата и при необходимости максимум две явно отмеченные альтернативы. Источники и технические evidence-ссылки не показываются в обычном ответе, кроме обязательной ссылки на найденный внешний лот, которого нет в Platforma. Полный запрос, ответ, использованные ревизии источников и evidence сохраняются в защищённом административном аудите без отдельной генерации цитат моделью.

Yandex Maps полностью удаляется из production runtime. Единый Map Module строится на MapLibre GL JS и используется картой каталога, картой карточки объекта и point picker внутри чата. OpenFreeMap является default Tile Provider. LocationIQ используется только на backend как Geo Provider для преобразования названия места или адреса в координаты. Фактический поиск RealEstateObject и связанных FeedUnit в радиусе выполняется PostGIS.

Если Geo Provider не может однозначно определить место, пользователь выбирает точку вручную. Карта открывается внутри окна чата, пользователь двигает карту под неподвижным центральным прицелом, выбирает радиус и подтверждает координаты. После подтверждения поиск выполняется PostGIS без обращения к LocationIQ.

## User Stories

### Доступ и оболочка чата

1. Как авторизованный пользователь Platforma, я хочу видеть кнопку помощника на каждой странице, чтобы начать поиск из любого раздела.
2. Как неавторизованный посетитель, я не хочу получать доступ к помощнику, чтобы внутренняя информация Platforma оставалась закрытой.
3. Как пользователь, я хочу открыть чат по клику на круглый логотип в правом нижнем углу, чтобы помощник не занимал экран постоянно.
4. Как пользователь desktop-версии, я хочу перетаскивать окно чата, чтобы оно не перекрывало важные данные страницы.
5. Как пользователь desktop-версии, я хочу изменять размер окна чата курсором, чтобы выбирать удобный объём переписки и карты.
6. Как пользователь, я хочу, чтобы позиция и размер чата сохранялись, чтобы не настраивать окно после каждого перехода.
7. Как пользователь, я хочу иметь только действие сброса позиции и размера, чтобы интерфейс не был забит лишними кнопками закрепления.
8. Как мобильный пользователь, я хочу открывать чат в полноэкранной sheet, чтобы им было удобно пользоваться пальцами.
9. Как пользователь клавиатуры, я хочу управлять чатом, картой и действиями через доступные focus states, чтобы интерфейс был доступным.
10. Как пользователь, я хочу продолжать текущий разговор после перехода между страницами Platforma, чтобы не повторять контекст.
11. Как пользователь, я хочу видеть историю своих разговоров за последние 30 дней, чтобы вернуться к недавнему поиску.
12. Как пользователь, я хочу видеть чип текущего ЖК, лота, застройщика или фильтров страницы, чтобы понимать, какой контекст получил помощник.
13. Как пользователь, я хочу удалить или заменить контекстный чип до отправки сообщения, чтобы случайный контекст не искажал запрос.

### Ответы и поиск предложений

14. Как пользователь, я хочу задавать тематические вопросы о недвижимости на русском языке, чтобы не осваивать специальный синтаксис.
15. Как пользователь, я хочу узнавать описание, локацию, архитектуру, инфраструктуру, наполнение и характеристики ЖК, чтобы быстро подготовиться к разговору с клиентом.
16. Как пользователь, я хочу получать актуальные цены и наличие из Platforma, чтобы опираться на приоритетный внутренний источник.
17. Как пользователь, я хочу получить цену с официального сайта застройщика, если в Platforma цена отсутствует, чтобы не потерять потенциальное предложение.
18. Как пользователь, я хочу видеть возраст цены и наличия в понятном виде, например «обновлено 10 часов назад», чтобы самостоятельно оценить свежесть.
19. Как пользователь, я хочу получать информацию об ипотеке, рассрочке и бонусах застройщика, чтобы сравнивать реальные условия покупки.
20. Как пользователь, я не хочу получать налоговые и юридические консультации, чтобы помощник не выдавал неподтверждённые правовые советы.
21. Как пользователь, я хочу искать проекты и лоты по бюджету, комнатности, району, метро, застройщику, сроку сдачи и другим доступным фильтрам, чтобы заменить ручной просмотр каталога.
22. Как пользователь, я хочу задавать фильтры свободным текстом, чтобы не заполнять длинную форму.
23. Как пользователь, я хочу получать один короткий составной уточняющий вопрос, когда без бюджета, комнатности или другой критичной информации поиск бессмысленен.
24. Как пользователь, я хочу, чтобы уже указанные условия не переспрашивались, чтобы диалог не раздражал.
25. Как пользователь, я хочу, чтобы помощник сначала сравнил все подходящие кандидаты, а затем выдал лучшие, чтобы результат не зависел от порядка источников.
26. Как пользователь, я хочу видеть максимум три основных результата, чтобы не разбираться в свалке карточек.
27. Как пользователь, я хочу видеть максимум две дополнительные альтернативы, если они действительно полезны, чтобы сохранить выбор без информационной перегрузки.
28. Как пользователь, я хочу, чтобы точные совпадения всегда шли раньше альтернатив, чтобы мои условия считались приоритетными.
29. Как пользователь, я хочу видеть явное объяснение каждого отклонения альтернативы, чтобы не принять её за точное совпадение.
30. Как пользователь, ищущий однокомнатную квартиру за 20 млн рублей, я хочу при отсутствии точного результата увидеть двухкомнатную за 22 млн в близком районе, чтобы рассмотреть осмысленный компромисс.
31. Как пользователь, я хочу допускать альтернативный бюджет в пределах примерно плюс-минус 5–7 млн рублей, если точных результатов нет, чтобы не потерять близкие предложения.
32. Как пользователь, я хочу допускать близкие районы, другую комнатность и другого застройщика только как обозначенные альтернативы, чтобы жёсткие условия не размывались молча.
33. Как пользователь, я хочу открыть карточку найденного ЖК или лота в Platforma, чтобы продолжить работу с существующими данными.
34. Как пользователь, я хочу получить прямую ссылку на лот на официальном сайте застройщика, если подходящего лота нет в Platforma, чтобы предложение не исчезло из ответа.
35. Как пользователь, я хочу видеть существующие PDF-презентации по выбранным ЖК и лотам, чтобы сразу использовать готовые материалы.
36. Как пользователь, я хочу, чтобы ответ начинался с формата «Лучшие по этим критериям», а альтернативы были отделены, чтобы структура ответа была предсказуемой.
37. Как пользователь, я не хочу видеть внутренние evidence-ссылки и длинные списки источников, чтобы ответ оставался человеческим.
38. Как пользователь, я хочу, чтобы помощник честно сообщил об отсутствии достаточных доказательств, чтобы не получить выдуманный ответ.

### Прогресс, ошибки и feedback

39. Как пользователь, я хочу видеть этапы «понимаю запрос», «ищу данные», «сравниваю варианты» и «формирую ответ», чтобы не думать, что система зависла.
40. Как пользователь, я не хочу видеть chain of thought модели, чтобы прогресс оставался понятным и безопасным.
41. Как пользователь, я хочу получить типичный ответ примерно за 10–15 секунд, чтобы поиск ощущался быстрым.
42. Как пользователь, я готов ждать дольше для сложного поиска рассрочек и скрытых условий, если помощник продолжает показывать прогресс и качество не ухудшается.
43. Как пользователь, я хочу повторить запрос после временной ошибки без дублирования сообщения, чтобы сетевой сбой не создавал несколько запусков.
44. Как пользователь, я хочу оценить ответ лайком или дизлайком, чтобы сообщить о качестве.
45. Как пользователь, я хочу при желании выбрать причину плохой оценки или оставить короткий комментарий, чтобы помочь ревьюеру.
46. Как пользователь, я не хочу, чтобы один ошибочный лайк или дизлайк немедленно переобучал систему, чтобы случайная оценка не ломала качество.

## Implementation Decisions

### Модули и Interfaces

- Новый предметный Assistant Module отвечает за conversation, query planning, retrieval orchestration, ranking, evidence, model routing, feedback и историю.
- HTTP controllers остаются тонкими границами. Persistence, external providers, background jobs и presentation logic не смешиваются в одном service.
- Основной пользовательский Interface — один authenticated conversation flow: создать или продолжить разговор, отправить сообщение, получать безопасные progress events, получить финальный ответ, оставить feedback и открыть свою историю.
- Shared contracts содержат только DTO, progress events, структуры ответа, карточек, фильтров, карты и feedback. Prisma, provider credentials, evidence internals и authorization остаются на backend.
- Новый provider-neutral Map Module предоставляет Interface для points, selected point, bounds changes, open/select actions, viewport, loading, error, fullscreen и optional overlays.
- Map Module имеет три consumers: catalog map, object detail location map и assistant point picker. Consumer-specific карточки и orchestration остаются в своих предметных областях.
- Tile Provider, Geo Provider и PostGIS Radius Search являются отдельными Seams. Замена одного слоя не требует изменения остальных.

### Auth, RBAC и rollout-доступ

- Все пользовательские endpoints защищаются существующей JWT/cookie авторизацией и server-side RBAC.
- Доступ к рабочим данным требует существующего permission чтения объектов. Frontend visibility не считается защитой.
- Для административного аудита вводится отдельное permission чтения assistant audit.
- Для source registry, ручного refresh и geo aliases вводится отдельное permission управления assistant sources.
- Новые permissions добавляются additive и не привязываются к названию конкретной роли.
- Rollout управляется feature flag и server-side pilot allowlist: сначала администраторы, затем существующая группа обычных пользователей, затем все авторизованные пользователи.

### Conversation, progress и UI

- Отправка сообщения создаёт persisted run с idempotency. Клиент получает run identity и подписывается на поток статусов.
- Поток передаёт только этапы и результат, но не chain of thought.
- Conversation, messages и runs сохраняются отдельно. Один пользователь может читать только собственные conversations.
- Плавающая кнопка отображается внутри существующего authenticated app shell на всех страницах. Новый router или global state manager не добавляется.
- Desktop chat является draggable и resizable, сохраняет geometry для пользователя и предоставляет только reset geometry. Pin и другие лишние controls отсутствуют.
- Mobile chat использует full-screen sheet.
- Обе версии поддерживают loading, empty, error, retry, stale response protection, AbortController, unmount cleanup, keyboard access и reduced motion.
- Контекст текущего ЖК, лота, застройщика или фильтров отображается removable chip до отправки сообщения.
- Chat показывает существующие project and lot presentation links, но не создаёт leads, tasks, CRM records или новые PDF.

### Persisted data и retention

- Для assistant вводятся предметные entities для conversations, messages, runs, evidence, feedback и AI usage. Training-таблицы не переиспользуются, потому что имеют другую предметную ответственность.
- Для knowledge ingestion вводятся Source Registry, Source Revision, normalized facts, searchable chunks и connector jobs.
- История conversations и полный assistant audit хранятся 30 дней.
- Анонимизированные агрегированные метрики хранятся 180 дней.
- Source revisions хранятся бессрочно.
- Статические факты могут жить бессрочно до появления новой canonical revision.
- Финальные пользовательские ответы не кешируются долгосрочно.
- Динамические retrieval-результаты могут кешироваться не более шести часов и инвалидируются изменением source revision.
- Цена и наличие Platforma читаются из текущей базы при каждом новом search run.

### Источники и ingestion

- Knowledge Source Registry является единственным реестром источников, их типа, canonical URL, приоритета, расписания, состояния и connector configuration.
- Source Connector Interface принимает запись реестра и возвращает нормализованный fetch result: HTTP metadata, content type, checksum, raw payload и найденные ссылки.
- Отдельный connector worker выполняет суточный cron, адресные refresh jobs, bounded retries, timeouts, безопасную классификацию ошибок, restart recovery и идемпотентную обработку.
- Пилот ingestion ограничен 20 ЖК от 5–7 застройщиков.
- В MVP реализуются connectors официальных страниц выбранных застройщиков и релевантных официальных страниц банков или promotions.
- Entry points агрегаторов CIAN, Домклик, Яндекс Недвижимость и Новострой-М существуют в выключенном состоянии; их отдельные production parsers не входят в MVP.
- Из публичных источников извлекаются HTML, DOM и JSON-LD. Скриншоты, OCR и visual extraction не используются.
- Raw HTML и JSON сохраняются сжато и неизменно как Source Revision.
- Source Revision имеет checksum, fetchedAt, HTTP metadata, статус обработки и связь с предыдущей revision.
- Неизменившийся checksum не создаёт повторную обработку или embeddings.
- Normalized facts и searchable chunks сохраняют provenance до Source Revision.
- Evidence для ответа составляется retrieval-слоем из уже использованных facts и chunks, а не отдельным модельным запросом.
- URL ingestion защищается allowlist реестра, проверкой protocol, DNS/IP от SSRF, redirect limits, content type и maximum response size.

### Приоритет источников и свежесть

- Официальная страница ЖК на сайте застройщика является canonical источником описания, архитектуры, инфраструктуры, наполнения и других статических характеристик.
- Platforma и её FeedUnit являются primary источником цены и наличия.
- Официальный сайт застройщика используется для цены и наличия, когда соответствующие данные отсутствуют в Platforma.
- Ипотека, рассрочка, скидки и бонусы берутся преимущественно с официальных страниц застройщика и банка.
- Агрегаторы могут быть supplementary evidence после подключения их parsers.
- Каждый normalized fact хранит source kind, source priority, observedAt или validFrom, fetchedAt и freshness.
- Конфликт разрешается детерминированной таблицей приоритетов, а не модельным предпочтением.
- Устаревшая, но полезная цена может показываться с явной маркировкой возраста. Свежесть не скрывается.

### Retrieval, query planning и ranking

- Retrieval объединяет structured SQL по RealEstateObject и FeedUnit, PostgreSQL full-text search, pgvector semantic search и source-priority rules.
- Модель не получает весь corpus и не выполняет поиск по своей памяти.
- Embeddings рассчитываются пакетно только для изменившихся chunks.
- Точный embedding model задаётся provider-конфигурацией и проверяется benchmark перед rollout.
- Query Planner преобразует пользовательский текст в валидируемое structured intent: task type, hard filters, soft preferences, anchor place, radius, required facts и необходимость clarification.
- Координаты, цены, availability, ссылки и source freshness никогда не принимаются из свободного текста модели без детерминированной проверки.
- Ranking сначала применяет hard filters, затем source freshness, relevance и soft preferences.
- Модель может объяснять ranking, но не обходить hard filters.
- Основной ответ содержит максимум три результата.
- Дополнительный блок содержит максимум две alternatives и только при доказанной полезности.
- Допустимые relaxations: близкий район, другой застройщик, другая комнатность и бюджет примерно плюс-минус 5–7 млн рублей.
- Каждое relaxation отображается пользователю явно.
- Если точный лот отсутствует в Platforma, но найден на официальном сайте застройщика, карточка обязательно содержит прямую внешнюю ссылку и freshness.
- User-facing answer не показывает evidence citations. Исключения: рабочие ссылки на карточки Platforma, существующие PDF, обязательная внешняя ссылка на отсутствующий в Platforma лот и map attribution.

### Model routing, validation и feedback

- Обычные запросы маршрутизируются в Luna reasoning medium.
- Сложные сравнения, неоднозначные условия и глубокий поиск promotions маршрутизируются в Luna reasoning high.
- После ответа выполняется детерминированная проверка schema, hard filters, evidence coverage, ссылок и свежести.
- При провале допускается один повтор через Terra reasoning medium.
- Luna max исключён.
- Feedback не меняет модель, prompt или ranking автоматически.
- Feedback попадает в human review queue и затем может стать частью versioned eval dataset.
- Assistant не выполняет online self-training и не меняет weights.
- Улучшения происходят через управляемые source revisions, prompt versions, retrieval/ranking changes и повторный eval.
- Audit сохраняет исходный запрос, финальный ответ, structured intent, applied filters, candidate set, ranking decisions, evidence revisions, provider routing, tokens, latency, error classification и feedback.

### Полный отказ от Yandex Maps и MapLibre migration

- Yandex Maps полностью удаляется из production runtime Platforma.
- Не остаются script loader, browser globals, frontend API key, env contract, Yandex-specific types, styles или fallback copy.
- MapLibre GL JS является разрешённой frontend dependency и единственной интерактивной картографической библиотекой web Platforma.
- Existing catalog behavior сохраняется: filters, point conversion, marker labels, marker selection, list synchronization, bounds-driven visible list, fullscreen и open-object action.
- Existing object detail behavior сохраняется: карта показывается только при валидной паре координат и использует текущую предметную информацию popup.
- OpenFreeMap является default Tile Provider Adapter и отдаёт style и vector tiles.
- OpenFreeMap и OpenStreetMap attribution отображается стандартным контролом карты и не скрывается CSS.
- OpenFreeMap не считается SLA-backed dependency.
- Style URL и provider enable state задаются runtime configuration, чтобы перейти к другому provider или self-hosted tiles без изменения Map Interface.
- Tile Provider failure не превращает property API или textual list в ошибку. Map consumer показывает fallback, а данные и ссылки остаются доступны.
- После включения MapLibre никакая page Platforma не должна загружать api-maps.yandex.ru или читать Yandex API key.

### Geo Provider и Place Resolver

- LocationIQ используется только как backend Geo Provider Adapter.
- Frontend не вызывает LocationIQ напрямую и не получает его API key.
- Geo Provider Interface принимает normalized text query и search context, а возвращает максимум три normalized candidates с coordinates, display label, confidence, provider identity и cache metadata.
- Геокодирование выполняется после отправки пользовательского запроса, а не на каждый введённый символ.
- Point picker не вызывает geocoder.
- Place Resolver использует следующий порядок: confirmed local alias; LocationIQ с country и relevant-city bounds; официальный адрес из Knowledge Base с последующим geocoding; ambiguous candidates; manual point.
- Если пользователь явно указал другой город, city context меняется до geocoding; жёсткое молчаливое ограничение Москвой не применяется.
- Geo aliases являются отдельными внутренними records с normalized text, coordinates, display label, scope, confirmation status, creator и timestamps.
- Provider request-response cache не используется как alias registry.
- Geo Provider cache соблюдает retention активного LocationIQ plan.
- Cache key включает normalized query, locale, country и viewbox context.
- Geo Provider calls имеют server-side timeout, bounded retry только для retryable failures, RPS limit, daily budget, circuit breaker и безопасную telemetry без credentials.

### PostGIS и Radius Search

- Текущие RealEstateObject latitude и longitude остаются canonical write fields, потому что их уже используют admin editing, map responses и presentations.
- Additive migration создаёт nullable database-derived geography Point с SRID 4326.
- Geography вычисляется только при наличии полной пары latitude и longitude; application code не записывает geography независимо.
- Geography получает GiST index.
- Старый обычный composite index удаляется только после проверки всех оставшихся consumers и query plans.
- Migration вычисляет geography для существующих объектов без изменения latitude и longitude.
- Старые применённые migrations не редактируются.
- Radius Search является частью backend Map domain.
- Radius Search принимает validated anchor coordinates, positive radius within configured bounds и существующие property filters.
- Radius predicate использует geography units in meters и index-aware PostGIS operation.
- Distance sorting возвращает distanceMeters.
- FeedUnit не получает отдельные coordinates в этой версии и участвует в геопоиске через связанный RealEstateObject.
- Spatial filter применяется вместе с существующими object и lot filters на server, а не к полному dataset только в browser.
- Map API response использует explicit serializer и не возвращает Prisma entities или geography internal representation.
- Geo response включает anchor, radiusMeters, radius GeoJSON polygon, result markers, distanceMeters и distinction between primary and alternative results.
- Radius polygon формируется server-side meter-correct способом. Screen-pixel circle MapLibre не изображает реальный радиус.
- Радиус всегда означает расстояние по прямой. UI не использует слова «пешком», «на машине» или «время в пути».

### Point picker и отображение георезультатов

- Point picker открывается внутри assistant chat surface. Отдельный browser popup или новая application route не создаётся.
- На desktop point picker заполняет большую часть draggable и resizable chat.
- На mobile point picker заполняет full-screen sheet.
- Центр выбора задаётся неподвижным crosshair. Пользователь двигает map viewport, а выбранными coordinates считаются coordinates центра.
- Point picker показывает radius chips 1, 2, 3 и 5 км, confirm и cancel actions.
- Текстовый query может передать другой валидный radius.
- До confirm изменение viewport не выполняет property search.
- После confirm frontend отправляет anchor coordinates и radius в backend.
- После подтверждения conversation context отображает removable и editable chip с выбранной точкой и радиусом.
- Результаты геопоиска показывают anchor marker, meter-correct radius polygon, максимум три primary markers и максимум две alternative markers.
- Перемещение уже подтверждённого anchor создаёт новый PostGIS search run и не вызывает LocationIQ.
- Map Module сохраняет viewport только там, где это требуется текущим consumer, и не создаёт глобальное скрытое состояние между несвязанными картами.

### Производительность, стоимость и безопасность

- Typical structured request имеет целевой пользовательский latency 10–15 секунд.
- Для сложного запроса качество имеет приоритет над лимитом; клиент всё время видит progress.
- Provider calls выполняются только server-side, с timeouts, bounded retries, rate limits, circuit breaker и суточными budget limits.
- Секреты и raw provider payload не попадают в обычные logs.
- Map views не вызывают LocationIQ и не расходуют geocoding credits.
- Повторный поиск вокруг известных coordinates выполняется только в PostGIS.
- MapLibre и PostGIS не создают per-view provider billing.
- OpenFreeMap используется как hosted default; self-hosting рассматривается после фактической telemetry.
- Production LocationIQ key, Tile Provider configuration и budgets находятся только в deployment secret configuration.
- Automatic tests используют fake Geo Provider и local deterministic map style/tile fixtures.
- Реальные provider calls, production enablement и массовая индексация выполняются только отдельным rollout-решением после пилота.

## Testing Decisions

- Основной и максимально высокий test Seam — один authenticated browser E2E flow поверх реального Nest application, disposable PostgreSQL/PostGIS, применённых migrations, fake Luna/Terra, fake Geo Provider, stub source connectors и локальной deterministic map style fixture.
- Основной flow отправляет сообщение как авторизованный пользователь и проверяет progress, clarification, retrieval, ranking, финальный ответ, history, feedback, evidence audit, переход к карточкам, map rendering, manual point и radius search.
- Хороший тест проверяет внешнее поведение и domain invariants: доступ, выбранные результаты, hard filters, freshness, количество alternatives, evidence coverage, видимые markers и provider degradation.
- Тест не проверяет private methods, внутренний порядок вызовов, точный prompt, MapLibre internals или точный порядок React effects.
- Основной flow покрывает factual answer, structured property search, comparison, exact match, relaxed alternative, external developer lot, stale price label, existing PDF links, no-evidence refusal, Luna route и Terra fallback.
- Основной flow покрывает 401, 403, чтение только собственных conversations, отдельные admin permissions и отсутствие evidence в обычном user contract.
- Persisted run и reconnect проверяются идемпотентно: повтор одного idempotency key не создаёт второй model run или второе сообщение.
- Browser flow покрывает существующую карту каталога, filters, marker/list synchronization, selected state, fullscreen, object detail map, assistant point picker и radius search.
- Browser flow проверяется в desktop и mobile viewport.
- Desktop покрывает drag/resize chat, fullscreen map, selection и point picker внутри окна.
- Mobile покрывает full-screen sheet, gestures, crosshair, radius chips, confirm и cancel.
- Existing Yandex marker behavior tests используются как prior art по labels, selected state, bounds и callbacks, но assertions переводятся на external behavior provider-neutral Map Interface.
- Catalog lot filter tests являются prior art для совместного применения object и FeedUnit filters.
- Object detail tests являются prior art для coordinate validation и conditional map rendering.
- Presentation tests подтверждают, что сохранение latitude и longitude не ломает существующие PDF snapshots и previews.
- Disposable PostGIS tests проверяют existing-coordinate backfill, null pair to null geography, point inside radius, point on accepted boundary, point outside radius, distance ordering и combined lot filters.
- Migration replay выполняется на чистой PostGIS database и upgrade scenario с существующими RealEstateObject coordinates.
- Query verification подтверждает использование GiST index для representative radius dataset без привязки к конкретному textual EXPLAIN output.
- API contract tests проверяют latitude, longitude, coordinate pair, non-positive radius, radius above configured maximum, Decimal serialization, distanceMeters, GeoJSON и отсутствие internal geography.
- Connector contract tests используют local stub HTTP server и сохранённые HTML/JSON-LD fixtures.
- Connector tests проверяют redirects, timeout, retry classification, unsupported content, maximum size, checksum no-op, revision chain и safe failure.
- Geo Provider tests проверяют successful resolution, zero results, ambiguous candidates, timeout, retryable 5xx, non-retryable 4xx, 429, circuit breaker и daily budget.
- Geo cache tests проверяют normalized cache key, hit without external call, expiry per configuration и isolation from confirmed aliases.
- Place Resolver tests проверяют alias-first, bounded provider resolution, official-address fallback, ambiguous response и manual-point fallback.
- Point picker test подтверждает, что pan до confirm не запускает search, confirm запускает один search, cancel не меняет context, change point не вызывает Geo Provider.
- Visual behavior tests проверяют anchor marker, true radius polygon, primary/alternative distinction, attribution, loading и tile failure fallback.
- Network assertions подтверждают отсутствие requests к Yandex domains и отсутствие LocationIQ calls при map views, manual point и moved anchor.
- Build/config tests подтверждают отсутствие Yandex frontend env contract, script loader и browser global dependency.
- Model tests используют fake Luna/Terra и проверяют routing contract, schema validation, one-fallback maximum, usage telemetry и refusal при недостаточном evidence.
- Ranking tests проверяют hard filters, exact-first, максимум 3 плюс 2, допустимые relaxations и явное описание отклонений.
- Source-priority tests создают конфликтующие факты и подтверждают: Platforma выигрывает по цене и наличию; официальный сайт ЖК выигрывает по статическому описанию; официальный developer или bank source выигрывает по promotion; freshness не скрывается.
- Retention tests проверяют удаление conversations и audit после 30 дней, сохранение anonymized metrics до 180 дней и отсутствие автоматического удаления Source Revision.
- Feedback tests подтверждают, что like/dislike создаёт review item, но не меняет prompt, ranking или model route автоматически.
- Accessibility tests проверяют labels, focus order, chat dialog/sheet semantics, map controls, confirm/cancel, keyboard interaction, touch targets и reduced motion.
- Автоматические tests не обращаются к OpenAI, LocationIQ, OpenFreeMap, Yandex, сайтам застройщиков, банкам или агрегаторам.
- Перед общим rollout выполняется versioned eval из 200 запросов: factual questions, search, comparison, mortgage/installment, no-data, conflicting sources, stale prices, geosearch, clarifications и alternatives.
- Eval является блокирующим: auth violations, hard-filter violations, source-priority violations, invented price/availability, unsupported links и evidence leakage имеют нулевую терпимость.
- Остальные quality и latency thresholds фиксируются в версии eval до запуска пилота и не меняются задним числом.
- После реализации запускаются targeted assistant/map/geo tests, API tests, web tests, полный build, полный test suite, browser E2E и git diff check.
- Реальные OpenFreeMap, LocationIQ или OpenAI smoke выполняются отдельно, вручную, с явным разрешением, bounded budget и без вывода credentials.
- Manual QA проверяет реальную cartography и русские labels в Москве, attribution, catalog map parity, object detail map, ambiguous POI, поиск возле Павелецкая Плаза, источники и сложные promotions.

## Out of Scope

- Публичный или анонимный доступ к помощнику.
- Создание leads, интеграция с amoCRM, отправка сообщений, бронирование, изменение объектов и другие действия от имени пользователя.
- Юридические, налоговые и иные правовые консультации.
- Генерация нового PDF по команде в чате; в MVP показываются только существующие документы.
- Реализация production parsers для CIAN, Домклик, Яндекс Недвижимость, Новострой-М и других агрегаторов; в MVP присутствуют только выключенные connector entry points.
- Обход авторизации, CAPTCHA, anti-bot barriers и получение непубличных данных.
- Извлечение данных через скриншоты, OCR или visual page parsing.
- Routing, directions, walking distance, driving distance, public transit и travel time.
- Satellite imagery, cadastral layers, terrain, 3D buildings и custom cartography beyond Platforma styling.
- Self-host OpenFreeMap tiles, Nominatim, Pelias или другой geocoder в первой версии.
- Automatic import of POI datasets beyond confirmed aliases и existing Knowledge Base.
- Geocoding каждого RealEstateObject: существующие coordinates остаются source data.
- Отдельные coordinates для FeedUnit.
- Redesign catalog filters, object cards, navigation или соседних разделов.
- Replacement coordinate mini-visualizations inside generated PDF, если они не используют Yandex runtime.
- Online self-learning, автоматическое изменение model weights, prompts или ranking по feedback.
- Luna max.
- Voice interface, user images и другие multimodal requests.
- Массовая индексация всех сайтов до прохождения пилота.
- Production provider purchase, credentials setup, production migrations, deployment и включение feature для всех пользователей.

## Further Notes

- Текущая Platforma уже имеет authenticated app shell, server-side RBAC, RealEstateObject с Decimal latitude и longitude, FeedUnit, защищённый map objects endpoint, PostGIS, existing project/lot PDF modules и OpenAI fake-provider patterns.
- Текущий Yandex renderer используется картой каталога и картой object detail. Полный отказ от Yandex является обязательным результатом, а не optional cleanup.
- Existing catalog map behavior является risk zone: filters, list-marker synchronization, selected state, fullscreen, mobile behavior и object detail map должны пройти parity gate.
- Presentation generation и preview используют latitude и longitude; canonical coordinate fields не удаляются и не переосмысливаются.
- OpenFreeMap является Tile Provider, а не geocoder или property search engine.
- LocationIQ является Geo Provider для coordinates, а не map provider и не source of property offers.
- PostGIS является единственным authority, определяющим, входит ли RealEstateObject в радиус.
- Map outage деградирует до usable textual list.
- Geocoder outage деградирует до manual point selection.
- Property API failure показывается отдельно и не маскируется как tile error.
- Expected cost shape: MapLibre library и PostGIS не добавляют per-view provider charge; OpenFreeMap отдаёт tiles; LocationIQ usage растёт только с unresolved text places.
- Точный платный LocationIQ plan или переход к self-host выбирается после pilot telemetry.
- Внутренний evidence audit не увеличивает tokens: provenance прикрепляется из retrieval results и source revisions.
- «Плохой результат» включает отсутствие известных подходящих вариантов, hard-filter violation, unsupported fact, stale price без маркировки, broken link, model fallback, provider error, latency over target или user dislike.
- User dislike является сигналом, а не истиной. Итоговая классификация выполняется человеком с evidence.
- Future roadmap сохраняет расширение Source Registry на все сайты, отдельные aggregator parsers, chat PDF generation и routing/time-in-transit search, но эти возможности не должны усложнять MVP заранее.
- Исходные GitHub issues #2 и #3 остаются историей обсуждения. Для реализации и декомпозиции используется только этот документ.
