# FIX-GEO2: Logical Plan V1 и гибридное время до метро

## 1. Поток запроса

- Frontend сразу отправляет и сохраняет исходный текст; предварительный геокодер больше не блокирует submit.
- Один глубокий Module `AssistantExecutionModule` с Interface `execute(runId, deadlineAt)` скрывает планирование, поиск, геометрию и маршруты.
- Luna/Terra получают полный сырой диалог и возвращают строгий `AssistantLogicalPlanV1`, а не SQL, координаты или цепочку tool calls.
- В первой версии новые предикаты только:
  - `SPATIAL / INSIDE / PLACE`;
  - `TRAVEL_TIME / WALK / NEAREST_METRO / LTE`.
- Существующие бюджет, комнаты и остальные фильтры остаются внутри того же плана; их отсутствие больше не вызывает обязательное уточнение.

## 2. Исполнение и гибрид маршрутов

- Backend проверяет, что названия, числа и единицы плана действительно взяты из запроса.
- `INSIDE` исполняется через `ST_Covers`. Для проверенных замкнутых колец сохраняются отдельно граница `LINE` и честная область `AREA`; никаких центроидов и буферов.
- Добавляются additive-таблицы:
  - серверный справочник `metro access points`;
  - лучший подтверждённый пеший маршрут от объекта до метро.
- Справочник загружается идемпотентно из версионированного OSM/OpenMapTiles-совместимого GeoJSON.
- Как на карте: выбираются три ближайшие точки доступа по прямой, существующий `MapRoutingService` считает пешие маршруты, сохраняется минимальное время.
- Запрос сначала использует материализованный факт. On-demand разрешён максимум для трёх отсутствующих объектов; больший пробел покрытия или сбой маршрутизатора даёт `UNAVAILABLE`, а не уточнение и не выдуманный результат.
- Факт инвалидируется при изменении координат объекта, версии справочника или routing profile. Новые hooks, queue и cron не добавляются — обновление выполняет отдельная идемпотентная команда.

## 3. Ответы и контракты

- Карточка использует существующий `facts` и показывает подтверждённое: `4 мин пешком до метро «Таганская»`.
- Уточнение допустимо только при реальной неоднозначности места, отсутствующем числовом значении или конфликтующих жёстких условиях.
- Пустая выборка возвращается как нормальный `NO_RESULTS`.
- Сбой данных, deadline или провайдера возвращается как структурированный `UNAVAILABLE`; Terra при этом не вызывается.
- Terra остаётся только fallback после успешно полученного, но не прошедшего локальную проверку плана Luna.
- В shared-контракте меняются только причины `CLARIFICATION` и новый `UNAVAILABLE`; endpoint отправки и формат карточек не ломаются.

## 4. Узкий scope и проверки

- Разрешённый scope: assistant frontend/backend, минимальный export маршрутизатора, shared assistant contract, additive Prisma migration и существующие assistant-тесты.
- Не трогаем feeds, training, sources, каталог, дизайн карты, auth, rollout-контур и соседние рефакторинги. Не добавляем зависимости и универсальный tool-loop.
- Не создаём новые тестовые harness/scripts: обновляем существующие planner, PostGIS и connected E2E проверки.
- Обязательные сценарии:
  - исходный запрос про Садовое кольцо и пять минут до метро сразу выдаёт подходящие карточки;
  - объект с маршрутом больше 300 секунд исключается;
  - неоднозначное место вызывает backend-уточнение;
  - отсутствие маршрутов даёт `UNAVAILABLE`;
  - широкий запрос без бюджета, комнат и локации исполняется.
- Проверки выполняются только с fake Luna/Terra/маршрутизатором и disposable PostGIS, затем существующие API/web tests и builds. Платные и production-вызовы не выполняются.
- Перед включением capability справочник метро и маршрутные факты должны иметь полное покрытие опубликованных объектов.

## Зафиксированные решения

- Для v1 используется семантика трёх ближайших `metro access points` и выбирается минимальное пешее время.
- За один запрос допускается максимум три on-demand промаха материализованного слоя.
- После реализации вручную проверяется точный запрос в локальном защищённом UI и совпадение показанного времени с картой.
