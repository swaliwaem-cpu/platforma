# AGENTS.md

## Назначение

Platforma — внутренняя брокерская платформа.

Этот файл содержит постоянные правила работы с проектом.

Исторические журналы, старые планы, отчёты, сгенерированные документы
и Git history не являются источниками текущих требований.

## Приоритет источников

Используй источники в следующем порядке:

1. Текущая задача пользователя.
2. Ближайший к изменяемому коду `AGENTS.md`, если он существует.
3. Текущий код, Prisma schema, package scripts и тесты.
4. Активная документация, относящаяся к конкретной области задачи.
5. Git history — только по прямому запросу или при расследовании регрессии.

Если источники противоречат друг другу:

- остановись;
- покажи конкретное противоречие;
- не выбирай молча удобный вариант.

Тесты описывают текущее поведение, но не отменяют явное новое требование
пользователя. При намеренном изменении поведения обнови тесты
и объясни изменение.

Frontend-задачи:

- `docs/FRONTEND_GUIDE.md`
- `docs/RISK_ZONES.md`

Backend, API и data-задачи:

- `docs/BACKEND_GUIDE.md`
- `docs/RISK_ZONES.md`

Тесты, Docker, миграции и deploy:

- `docs/TESTING_AND_DEPLOY.md`
- `docs/RISK_ZONES.md`

Читай только документы, относящиеся к текущей задаче.

Не читай весь каталог `docs` перед каждой работой.

## Не являются инструкциями

Не используй по умолчанию как требования:

- старые планы;
- завершённые отчёты;
- журналы изменений;
- `docs/superpowers/**`;
- архивные документы;
- generated-файлы;
- Git history;
- старые комментарии и TODO без подтверждения текущим кодом.

Обращайся к ним только по прямому запросу пользователя
или при расследовании конкретного исторического решения.

## Перед работой

1. Проверь:
   - `git branch --show-current`
   - `git status --short`

2. Не переключай ветку без разрешения пользователя.

3. Не откатывай и не удаляй пользовательские или чужие изменения.

4. Изучи реальные package scripts перед запуском команд.

5. Найди все использования файлов и символов,
   которые планируешь менять.

6. Определи минимальный scope задачи.

7. Если бизнес-поведение действительно неоднозначно
   и текущий код не даёт ответа, задай один конкретный вопрос.

8. Перед изменениями, затрагивающими более пяти файлов,
   auth/RBAC, Prisma, migrations, storage или deploy,
   дай короткий план.

Если пользователь уже дал подробный утверждённый план,
не требуй повторного подтверждения того же самого.

## Субагенты

Для крупных задач разрешено использовать субагентов.

Предпочтительная схема:

1. Несколько read-only субагентов исследуют независимые области.
2. Главный агент объединяет результаты.
3. Только главный агент изменяет общий worktree.
4. После изменений read-only субагенты проверяют конкретный scope.

Не разрешай нескольким агентам одновременно изменять один worktree,
если пользователь явно не запросил отдельные worktrees.

## Правила изменений

- Меняй только то, что необходимо для текущей задачи.
- Не выполняй попутный рефакторинг.
- Не добавляй зависимости без явной необходимости и разрешения.
- Не создавай инфраструктуру «на будущее».
- Не переписывай работающий участок целиком без доказанной причины.
- Не меняй публичные API и shared contracts молча.
- Не меняй auth/RBAC только во frontend.
- Backend всегда является источником проверки доступа.
- Не создавай generic `utils.ts`, `helpers.ts` и `common.ts`
  для несвязанных обязанностей.
- Не дублируй существующую реализацию
  без проверки возможности её повторного использования.
- Не выполняй массовое форматирование несвязанных файлов.
- Не редактируй `dist`, `node_modules`, `*.tsbuildinfo`
  и generated output вручную.
- Не изменяй lockfile, если зависимости не менялись.

Количество строк и файлов не является самостоятельной целью.

Предпочитай цельный читаемый файл нескольким мелким файлам,
между которыми распределена одна ответственность.

Разделяй код только если выделяемая часть:

- имеет самостоятельную предметную ответственность;
- меняется по другой причине;
- имеет собственные зависимости или lifecycle;
- используется несколькими consumers;
- может тестироваться независимо;
- заметно уменьшает связность исходного файла.

Не выноси в отдельный файл только ради уменьшения LOC:

- локальные типы;
- одноразовые constants;
- private helpers;
- DTO одного controller;
- mapper или serializer с одним consumer;
- небольшие validators;
- barrel-файлы `index.ts`.

Ориентиры являются сигналом для проверки, а не лимитом:

- до 900 строк допустимо при одной ясной ответственности;
- 900–1200 строк требует проверки смешения обязанностей;
- более 1200 строк требует архитектурного объяснения.

Не объединяй самостоятельные routes, controllers или lifecycles
только ради уменьшения количества файлов.

Бюджет файлов используется для обнаружения архитектурного конфетти,
но не является критерием успешности сам по себе.

## Git и данные

Запрещено без прямого разрешения:

- `git reset --hard`;
- удаление чужих веток;
- destructive checkout;
- `prisma migrate reset`;
- `prisma db push` для shared, staging или production базы;
- изменение уже применённых migration-файлов;
- удаление production volumes;
- destructive rollback базы.

Новые миграции должны быть additive,
если пользователь не утвердил отдельный план изменения данных.

## Секреты и внешние сервисы

- Не коммить `.env`, ключи и токены.
- Не выводи секреты в logs и финальный ответ.
- Не выполняй реальные платные или production-вызовы,
  если задача явно этого не разрешает.
- Автоматические тесты используют fake или stub providers.
- Не подключайся к production по SSH
  без прямой команды пользователя.

## Проверки

После изменения:

1. Запусти targeted tests изменённой области.
2. Запусти соответствующий workspace build.
3. При cross-cutting изменениях запусти:
   - `pnpm test`
   - `pnpm build`
4. Не удаляй и не ослабляй тесты ради зелёного результата.
5. Не добавляй `.only` и `.skip`.
6. Не утверждай, что проверка выполнена,
   если команда фактически не запускалась.

## Финальный ответ

Кратко укажи:

- что сделано;
- какие файлы изменены;
- какие проверки запущены и с каким результатом;
- что требуется проверить вручную;
- какие риски или спорные места остались.
